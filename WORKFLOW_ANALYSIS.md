# Workflow maintenance summary

This is a human-facing explanation, not an additional skill or runtime instruction file.

## Decisions retained

One Reviewer persona covers compliance and engineering quality. Fresh review contexts remain independent; the Builder is warm only for the current task. Models, reasoning efforts, permissions and public commands are unchanged. Specification owns semantics; planning resolves consequential interfaces, dependencies, production integration and proof strategy without producing a duplicate implementation. Ordinary local coding and equivalent command corrections remain with Builder.

The ordinary workflow is an initial build/review, at most one ordinary repair, then acceptance. A second repair requires a justified change of context or capability. A real remaining blocker is never waived to satisfy a cap. No CI, new workflow engine, permanent daemon or additional review persona was added.

## Changes in this snapshot

- Remove the controller's duplicate whole-plan technical audit; keep the compact task index, prescribed baseline and mechanical recovery checks. Strengthen Planner's own fresh-agent readiness check and Specifier's concrete semantic examples.
- Bind the initial review range to generated contract metadata. A repair begins at the predecessor packet's candidate, not an arbitrary partial task diff.
- Schema-2 reports bind the exact package digest. The gated helper verifies that the package matches Git, contract and supplied predecessor/final-validation evidence. This re-render is local deterministic work; no diff is relayed into controller context.
- Preserve all blockers through same-candidate clarification, including BLOCKED results. Clarification requires explicit per-ID evidence and does not increment repair count. Packets carry review family and count so repairs cannot change families or silently exceed their limit.
- Require an explicit PASS declaration for required build checks. Final validation must exist and name the exact candidate; the package binds its content. Historical RED and unrelated baseline failures are reported separately.
- Validate recovery counters and accepted report/package references. Record a nonignored-input baseline and reject new/changed untracked inputs during candidate checks. Minor IDs refer to their original report without another prose packet.
- Restore the full questionnaire, remove only five obsolete review templates, preserve unrelated repository source byte-for-byte, and include local negative/positive regression tests.

## Scope of assurance

These helpers detect specified accidental evidence/state errors when invoked. They are not an adversarial security system, do not verify the truth of model-written results and cannot force an agent to use the gates. The untracked-input check is not hermetic: ignored files, environment, dependencies and toolchains still require appropriate validation. Recovery needs intact, correctly recorded predecessor references; wholesale loss or rewriting of all local evidence cannot be reconstructed by a checksum alone.

Schema-1 active reports require bounded migration. Do not relabel them PASS, reset counters, delete evidence or rerun accepted implementation merely to satisfy formatting. Recreate the bounded contract/package from actual Git state and ask the owning role only for missing evidence or judgment. A material semantic change still requires the human.

## Why these changes are small in operation

The five existing helpers and five public skills remain the runtime surface. No extra default agent, review stage or test suite is inserted into downstream projects. The new metadata is generated or checked mechanically. Full logs and findings remain in files. The controller only routes validated status and references, with technical exceptions sent to their existing owners.

Design adaptations come from agent-skills' selective context and anti-paraphrasing guidance, Superpowers' file-based task handoffs and scoped review, and the distinction between deterministic invariants and model judgment. See SOURCES.md for references. No benchmark or upstream model result is treated as a measured improvement for PulseBeam. Actual cost, loop frequency and autonomous flow remain to be measured with the unchanged models.
